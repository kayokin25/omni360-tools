# Панель инструментов Omni360 — исходники сборки

Три Python-скрипта перенесены в браузер и вшиты в панель как обычные инструменты
(рядом с калькулятором OmniBuy и картой-компаньоном):

| Карточка в панели | Было | Стало |
|---|---|---|
| Сбор технических требований | `тт/новое/tt.py` | `tools/techreq.html` |
| Сортировка креативов | `подбор крео/match_creatives.py` | `tools/creatives.html` |
| Подбор адресов | `поиск адресов/script.py` | `tools/addresses.html` |
| Объединение таблиц | `поиск адресов/твига merged/merge.py` | `tools/merge.html` |

Ещё два инструмента пришли из исходной панели, теперь их исходники тоже здесь:
`tools/omnibuy.html` (калькулятор надбавки) и `tools/map.html` (карта-компаньон).
При сборке они заменяют одноимённые ресурсы в панели по существующему uuid.

Ничего ставить не нужно: ни Python, ни pandas, ни openpyxl, ни ffmpeg.
Всё считается в браузере, файлы не уходят на сервер.

## Сборка

```bash
python build.py
```

Складывает результат в `dist/` — это же и есть публикуемая папка:

* `dist/index.html` — панель целиком, один файл.
* `dist/tools/*.html` — те же инструменты по отдельности, если нужна прямая ссылка на один.

`build.py` берёт чистую панель из `source/`, добавляет три инструмента в её
`__bundler/manifest` (gzip+base64) и `__bundler/ext_resources`, а в шаблоне заменяет
карточки-заглушки (`note:`) на настоящие `src:` c iframe.

`dist/` намеренно лежит в репозитории: Netlify ничего не собирает, а просто раздаёт
готовую папку. Поэтому **после правок в `lib/` или `tools/` нужно прогнать `python build.py`
и закоммитить `dist/`** — иначе на сайте останется прежняя версия.

## Деплой

Netlify раздаёт `dist/` и поднимает две функции из `netlify/functions/`.
Настройки — в `netlify.toml`, менять в интерфейсе Netlify ничего не нужно, кроме одного:

| Переменная | Значение |
|---|---|
| `GIS_API_KEY` | ключ с dev.2gis.ru |

Задаётся в **Site configuration → Environment variables**. После добавления нужен redeploy.

### Почему ключ 2ГИС не лежит в коде

Репозиторий публичный, поэтому ключа нет ни в нём, ни в исходнике страницы: браузер
обращается к `/api/2gis`, а ключ подставляет функция `netlify/functions/gis.mjs`
из переменной окружения. Пользователь ничего не вводит.

Что это даёт и чего не даёт:

* ключ **нельзя утащить** со страницы и использовать в своих скриптах;
* но сам адрес панели публичный — кто знает URL, тот сможет искать через прокси.
  Проверка `Referer` отсекает встраивание с чужих сайтов, но не прямые запросы.
  Если нужно закрыть доступ целиком — это password protection / access control
  на платном тарифе Netlify.

В `build.py` есть страховка: сборка падает, если в собранные файлы попал ключ
или любой незнакомый uuid.

### Проверить локально, без Netlify CLI

`dev-server.mjs` раздаёт `dist/` и повторяет маршруты `/api/*`:

```bash
GIS_API_KEY=<ключ> node dev-server.mjs
```

Дальше открыть <http://localhost:8971>.

Отдельно проверить сами функции (реальные запросы к 2ГИС и Nominatim):

```bash
GIS_API_KEY=<ключ> node netlify/functions/test_functions.mjs
```

### Если в `tt.py` поменялись длительности или алиасы операторов

Словари не дублируются руками — они генерируются из самого `tt.py`:

```bash
python lib/gen_tt_data.py
python build.py
```

`gen_tt_data.py` импортирует `tt.py` и выгружает `INVENTORY_DURATIONS` (269 пар),
`OPERATOR_ALIASES`, правила Russ/MAER/LBL и ссылку на папку Диска в `lib/tt-data.js`.
Путь к `tt.py` — константа `TT` в начале генератора.

Инструкция для того, кто выгружает и загружает ТТ, — [`docs/tt-upload.md`](docs/tt-upload.md):
как называть файлы, что обязательно публиковать по отдельности и как проверить
себя. Её можно давать новому сотруднику как есть. PDF-версия для отправки
собирается из того же файла:

```bash
python docs/md2pdf.py docs/tt-upload.md
```

Сам PDF в репозитории не лежит — он полностью выводится из `.md`, и держать
рядом две версии одного текста значит однажды разослать устаревшую.

### Если ТТ на Диске есть, а ссылка не находится

Скорее всего, имя файла расходится с названием оператора в АП. Лечится алиасом
в `OPERATOR_ALIASES` (слева — как в АП, справа — как в имени файла), после чего
`gen_tt_data.py` + `build.py`.

Сверка всех 95 файлов папки с 146 операторами справочника нашла семь таких
случаев — для них алиасы уже добавлены:

| файл на Диске | оператор в АП | что расходилось |
|---|---|---|
| `3Арт общее` | 3 Арт | нет пробела |
| `Zvenboard 416х572` | РА Zvenboard | нет «РА» |
| `Оди Медиа 576х288` | РА Оди Медиа | нет «РА» |
| `АРК общее` | АРК Медиа | нет «Медиа» |
| `ГиГ общее` | Рекламное агентство «ГиГ» | другое название |
| `Постекст 640х480` | Постекс | лишняя «т» в файле |
| `Рекламная группа 6х3 общее` | Рекламная группа 6х3" | «6х3» разбирается как разрешение 6x3 |

Ещё три файла алиасом не лечатся — там нужно переименование на Диске, иначе
станет хуже (алиас перекинул бы оператора на один файл и отобрал бы у него
остальные):

* `2 Этаж 3к1.png` — «3к1» не распознаётся как соотношение `3:1`; нужно
  `2 Этаж 3:1.png`. Пока оператор закрыт файлом «2 Этаж общее».
* `Афиша 1200х600.jpg` — нужно `РА Афиша 1200х600.jpg`. Есть «РА Афиша 2:1»,
  и алиас отобрал бы его.
* `Диджитал Сан 720х360.png` — нужно `РА Диджитал Сан 720х360.png`. Есть
  «РА Диджитал Сан общее», и алиас отобрал бы генерик у всех разрешений.

Четыре файла `Аляска …` — просто дубликаты `РА Аляска …` с теми же
разрешениями, трогать нечего.

Проверить, что ничего не потерялось, можно так: у каждого файла берём
`parseFilename`, у каждого оператора — `operatorToken`, и смотрим, у каких
файлов токен не совпал ни с одним оператором.

## Чем проверялось

Порт сверялся с оригинальными скриптами на реальных данных, а не «на глаз»:

* **ТТ** — `tt.py` и инструмент прогнаны на одной и той же АП
  (`AP_tiest_868095279752977635.xlsx`): 60 строк → 5 после дедупликации, 4 ссылки,
  одна и та же связка без ссылки. Выгруженные xlsx совпадают ячейка в ячейку,
  включая адреса гиперссылок.
* **Креативы** — на настоящем архиве `new 13.07.zip` (1,3 ГБ, 108 видео) и
  `AP_Go_866940235059044833.xlsx`. Совпало всё: 12 связок, 8 закрыто, 4 не хватает,
  3 файла в архив (было 5 — до правила «один, самый большой файл на
  соотношение», см. ниже). Все четыре листа отчёта идентичны
  `Отчет_подбор_крео.xlsx`, а извлечённые видео совпадают по SHA-256 с
  `Крео_для_загрузки.zip`.
* **Адреса** — живой прогон по 2ГИС и Nominatim из браузера.

Тесты лежат в `lib/test_*.mjs` (node) и `lib/diff_*.py`, `lib/validate_out.py` (сверка
с Python и проверка xlsx через openpyxl):

```bash
node lib/test_lib.mjs
node lib/test_tt.mjs
node lib/test_creatives.mjs
```

## Сортировка креативов: один файл на соотношение сторон

Раньше правило подбора для не-Russ операторов брало САМЫЙ БЛИЖНИЙ по размеру
подходящий файл (тот же AR, размер ≥ экрана, из подходящих — с наименьшей
площадью). На реальной адресной программе это давало по несколько разных
файлов на одно и то же соотношение сторон — например, отдельно 576×288,
720×360, 960×480, 540×270 при том, что все они 2:1.

Так это не совпадает с тем, как крео грузят на практике: создают запись
креатива, отмечают галочками подходящих операторов и грузят ОДИН файл сразу
на всех — экран с любым размером не больше файла тут же отмечают той же
галочкой. Правило исправлено на: внутри одного соотношения сторон — только
самый большой доступный файл, он покрывает все экраны этого соотношения
размером не больше себя (Russ Outdoor не участвует — ему нужен только точный
размер, без исключений).

Поскольку все файлы внутри одного соотношения сторон растут пропорционально,
сравнение по площади равносильно сравнению по любой стороне — больший файл
всегда покрывает всё, что покрывает меньший, специального перебора не нужно.

Правило поменяно и в источнике (`match_creatives.py`), и в порту
(`lib/creatives-core.js`) одинаково — сверено повторным прогоном на тех же
`AP_Go_866940235059044833.xlsx` + `new 13.07.zip`: было 5 файлов в архиве на
8 закрытых связок, стало 3 (600×300 и 540×270 из группы 2:1 теперь покрывает
файл 720×360 той же группы). «Лишние видео» объясняет каждый файл отдельно:
дубль по точному размеру или просто меньше уже выбранного файла своего
соотношения.

### «Отправка» — раскрывающийся список, а не плоская таблица

Лист «Отправка» сгруппирован по файлу через настоящую группировку строк
Excel (те самые [+]/[-] слева, `outlineLevel` + `sheetPr/outlinePr
summaryBelow="0"`, чтобы заголовок группы был НАД операторами, а не под
ними): заголовок группы — сам файл креатива (разрешение, AR, длительность),
под ним — операторы, которым его грузить. Если у оператора несколько экранов
ОДНОГО соотношения сторон (внутри одной группы оно всегда одно — иначе файл
был бы другим), их разрешения сведены в одну строку через запятую — так их и
отмечают галочками разом. Колонка «Кол-во ФО» убрана — не несла пользы для
самого процесса загрузки.

Реализовано и в `match_creatives.py` (`openpyxl`, `row_dimensions[r].outlineLevel`),
и в `lib/creatives-core.js` + `lib/omnilib.js` (`writeXlsx` теперь понимает
строки-объекты `{cells, outlineLevel}` вдоль старого формата — плоского
массива, так что остальные инструменты не затронуты).

При переносе всплыл скрытый баг в самом Python-скрипте: пустая
строка-разделитель между группами (`ws.append([])`) не работала никогда —
`openpyxl`'s `ws.max_row` считает только строки с реально записанными
ячейками, поэтому следующая явная запись в `ws.max_row + 1` просто занимала
тот же номер строки, и разделитель бесследно пропадал (без ошибок — код
«отрабатывал» молча). Исправлено на собственный счётчик строк вместо
`max_row`; проверено построчным сравнением через `openpyxl.load_workbook`
на реальном отчёте — разделители и `outlineLevel` совпадают у Python и у
JS-порта, обе версии одинаково открываются, разворачиваются и сворачиваются.

## Объединение таблиц и история запросов

`merge.py` умел одно: склеить файлы вида «Название / Широта / Долгота», взяв шапку
из первого и копируя строки по позициям столбцов. В инструменте то же, но столбцы
по умолчанию сопоставляются **по названию** — файл с другим порядком колонок не
превращается в кашу, а свои столбцы из других файлов дописываются в конец шапки.

Сверено с оригиналом: на 36 файлах из `твига merged` и `merge.py`, и инструмент
дают одинаковые 2833 строки, лист и формат координат совпадают ячейка в ячейку.

Попутно выяснилось, почему лежащий там `0Все_города.xlsx` содержит 5666 строк
вместо 2833: `merge.py` исключает из входа только файл с именем ровно
`Все_города.xlsx`, поэтому после переименования результата следующий прогон
склеил таблицу с самой собой. Каждая строка в этом файле встречается чётное
число раз. Инструмент так не умеет — файлы выбираются вручную, — но **всегда
показывает число полных дублей**, даже когда их не убирает: именно этот счётчик
сразу выдал бы удвоение.

История в подборе адресов лежит в `localStorage` (`lib/history.js`): неделя,
20 записей и лимит по объёму, дальше вытесняется самое старое. Смысл — чтобы F5
не стирал сделанную работу. Выделенные записи склеиваются тем же ядром
(`lib/merge-core.js`), к строкам добавляется столбец с источником, а совпадающие
объекты убираются: один и тот же адрес мог попасть в два разных запроса.

## Добавление азимутов

### Инвентарь встроен, а не загружается пользователем

Источник (`screen_id`/`azimuth`) — всегда один и тот же файл, его прислали
один раз. Поэтому его не нужно прикладывать каждый прогон: он лежит в
`data/inventories_sync.xlsx` (~6,5 МБ, в `.gitattributes` помечен `binary`,
чтобы git не тронул переводы строк внутри ZIP), `build.py` копирует его в
`dist/data/` как обычный статический файл, а `tools/azimuth.html` подтягивает
его через `fetch()` сам, при открытии инструмента.

Важное: `fetch` идёт по **абсолютному** URL (`location.origin + '/data/…'`),
не по относительному — та же причина, что и у эндпоинтов подбора адресов:
документ открыт на `blob:` внутри панели, и относительный путь от него не
резолвится. `netlify.toml` держит для `/data/*` заголовок `Cache-Control:
no-cache` — не «не кэшировать», а «спросить сервер, не изменился ли файл»:
повторные открытия почти бесплатны, а после обновления файла всем сразу
отдаётся новая версия.

**Не встроено в общий бандл панели (`dist/index.html`).** Тот собирается в
один HTML на все восемь внутренних инструментов и открывается при каждом
визите в панель, даже если человек не трогает добавление азимутов, — раздувать
его на 6,5 МБ ради одного инструмента того не стоит. Раздельная статика
означает, что этот вес платит только тот, кто реально открыл именно этот
инструмент.

**Если инвентарь обновился:** заменить `data/inventories_sync.xlsx`, поправить
дату в константе `INVENTORY_UPDATED` в начале скрипта `tools/azimuth.html`,
пересобрать (`python build.py`) и закоммитить. Дата не вычисляется из
содержимого файла — там нет столбца с датой выгрузки, поэтому это ручная
пометка, синхронизируемая с заменой файла.

Порт `add_azimuth.py`, но устроен принципиально иначе, чем ТТ/креативы/объединение.
Те строят новый xlsx с нуля через `readXlsx`/`writeXlsx` — значения читаются, стили
не сохраняются, пишется наш фиксированный набор стилей. Для этой задачи так нельзя:
цель — добавить в существующую «эфирку» ровно один столбец, не трогая остальное
(стили, объединённые ячейки шапки, ширину столбцов, гиперссылки на фотоотчёты).

Поэтому `lib/azimuth-core.js` не пересобирает файл, а **хирургически правит XML
одного листа внутри ZIP**: правки — точечные замены подстрок по смещениям в
исходном тексте (без DOMParser, тем же регулярочным приёмом, что и весь остальной
`omnilib.js`), применяются от конца строки к началу, чтобы более ранние смещения не
сдвигались. Все остальные записи архива (стили, связи, гиперссылки, другие листы)
копируются в новый ZIP **байт-в-байт**, без разбора. Стиль новых ячеек не собирается
заново из шрифта/заливки/рамки — переиспользуется целиком индекс стиля (`s=`)
соседней ячейки GID той же строки: визуально то же самое, что в Python-версии, без
риска собрать стиль неточно.

### Найденный и исправленный баг: терялась первая строка данных

В `add_azimuth.py` (и в порту — до исправления) строка, с которой начинаются
данные, определялась эвристикой «после шапки идёт подзаголовок, если в
следующей строке есть хоть одно непустое значение». У настоящей строки данных
значения есть **всегда**, поэтому для эфирок с одностроч­ной (не объединённой)
шапкой первая строка данных под это условие тоже попадала и **пропускалась
молча** — её «Азимут» оставался пустым, без единой ошибки в логе.

Подтверждено на реальных файлах: у `Efirnaia_spravka_Dom_RF_Flait_3_SPB…xlsx`
(5 строк данных) обрабатывалось только 4, а `SPBB01406B1` — первая строка — не
получала азимут никогда, независимо от того, был ли он в источнике.

Исправлено на правильный признак: пустая именно **ячейка GID** в строке сразу
после шапки (у данных она есть всегда, у подзаголовка — никогда), а не «в строке
есть хоть что-то». Исправление внесено в сам `add_azimuth.py` и туда же, где
хранится источник правды для этого скрипта, — так следующий человек, который
откроет файл, увидит причину прямо в докстринге функции.

### Найденный и исправленный баг: жадный regex в omnilib.js склеивал ячейки

Отдельно, при сверке на настоящем 37-тысячестрочном инвентаре, нашёлся баг в
разборе xlsx самого `omnilib.js` — `parseSheetXml`, который используют **все**
инструменты через `readXlsx`, не только этот. Самозакрывающаяся пустая ячейка
(`<c t="inlineStr"/>` — Excel так пишет стилизованную, но безо всякого значения
ячейку, обычное дело в выгрузках) при жадном `[^>]*` в регулярке иногда
склеивалась со СЛЕДУЮЩЕЙ ячейкой: движок сначала жадно съедал атрибуты вплотную
до `/>`, альтернатива «самозакрывающийся тег» не находила на новой позиции
нужный символ и отступала, а альтернатива «открывающий тег с телом» охотно
дотягивалась до чужого закрывающего `</c>`. Результат — одна ячейка пропадала,
а следующая получала не своё значение, без единой ошибки в консоли: 2359 из
37213 строк (6,3%) в этом конкретном файле были сдвинуты.

Исправлено заменой `[^>]*` на ленивый `[^>]*?` в обоих местах (`omnilib.js` и
`azimuth-core.js`). Проверено, что регресса нет: фикстуры ТТ и креативов
(`AP_tiest…xlsx`, `AP_Go…xlsx`) этот паттерн не содержат, `test_lib.mjs`,
`test_tt.mjs`, `test_creatives.mjs` проходят с теми же цифрами, что и раньше.
Тем не менее если какой-то файл из внешнего экспорта (не из наших же
инструментов) в прошлом обрабатывался ТТ/креативами/объединением и в нём
встречались стилизованные пустые ячейки — тот прогон стоит повторить.

Проверялось на четырёх настоящих эфирках разной структуры шапки (одностроч­ная,
двухстроч­ная объединённая с shared strings, трёхстроч­ная с отдельным
подзаголовком) и сверялось с исправленным `add_azimuth.py`: совпадение и по
строке начала данных, и по числу совпавших/несовпавших GID, во всех четырёх
файлах. Синтетические фикстуры — в `lib/test_azimuth.mjs`.

## Гайды

У каждого инструмента, включая два внешних сервиса, есть свой гайд: кнопка
«Гайд» в карточке и в шапке открытого инструмента. Пять слайдов — зачем это
нужно, шаги, живое мини-демо, частые ошибки, связки с другими инструментами.
Пока гайд не открывали, на кнопке стоит точка; прочитанные лежат в
`localStorage` под `omni360.guideSeen`.

Гайд — такая же страница в iframe, как инструмент (`tools/guide.html`), а какой
именно показывать, задаёт `#tool=<id>`. Из iframe наружу общаемся `postMessage`:
открыть инструмент, открыть его с демо-данными, закрыться, отметиться
прочитанным. Прочитанные хранит панель, а не гайд: у неё один `localStorage` на
всё, а документ с `blob:`-адресом дотягивается до него не в любом браузере.

**Тексты и цифры — в `lib/guide-data.js`.** Оценки экономии собраны в одной
таблице `SAVINGS` в начале файла и больше нигде не повторяются: время «руками» —
прикидка, и в интерфейсе так и подписано. Что помечено «замер» — измерено на
настоящих файлах.

Мини-демо считают **настоящим кодом инструментов**, а не пересказом:

| Инструмент | Демо | Чем считается |
|---|---|---|
| ТТ | оператор + формат → длительность | `TTCore.lookupDuration` по `tt-data.js` |
| Креативы | экран → какой крео уйдёт | правило из `creatives-core.js`, `OmniLib.reduceRatio` |
| Адреса | снятие дублей по координатам | те же правила, что в ядре |
| Объединение | склейка трёх таблиц с разным порядком столбцов | `MergeCore.mergeTables` |
| Калькулятор | надбавка от стоимости подрядчика | формула калькулятора |
| Карта | координаты → ссылки на Яндекс/2ГИС/Google/OSM | те же шаблоны адресов |
| Мониторинг | темп и рекомендуемый лимит | пороги сервиса: <70% красный, <95% жёлтый |
| Планировщик | что заполняется на каждом из 4 шагов | — |
| Азимуты | разбор шапки на двух примерах (обычная / с подзаголовком) | `AzimuthCore.parseRows`/`findHeaderCell`/`detectDataStart` |

Смысл именно в этом: гайд, который пересказывает поведение своими словами,
рано или поздно начнёт врать про соседний изменившийся код.

### Демо-прогон по `#demo=1`

С последнего слайда можно открыть инструмент сразу с демо-данными — у пяти
инструментов это настоящий прогон, а не картинка:

* **объединение** — четыре файла `.xlsx` создаются на месте нашим же кодом
  записи; четвёртый специально «прошлый результат», чтобы был виден счётчик
  дублей (14 строк, 6 дублей);
* **ТТ** — демо-АП из настоящих связок справочника, разрешения подобраны под
  реально лежащие на Диске ТТ: 7 строк из 8 со ссылкой и длительностью, одна
  связка намеренно отсутствует;
* **адреса** — настоящий запрос «Пятёрочка / Казань», до 60 объектов;
* **калькулятор** — подставляет 500 000 ₽ и считает;
* **азимуты** — демо-инвентарь на 3 объекта и эфирка с одностроч­ной шапкой,
  собранные на месте; одна строка намеренно без совпадения.

Пояснение к демо выводится плашкой `.note info` под заголовком, а не в лог:
обработчик запуска лог очищает, и подпись исчезала ровно тогда, когда была нужна.

У сортировки креативов демо-прогона нет: для него нужен настоящий архив с
видео, а размеры читаются из самих файлов. В гайде так и написано.

## Порядок карточек

Карточки внутренних и внешних инструментов перетаскиваются мышью, порядок лежит
в `localStorage`. Перенос между секциями не разрешён — «внутренний» и «внешний»
это разное поведение, а не оформление. Новый инструмент добавляется в конец, уже
настроенный порядок не ломая; рядом с заголовком есть «сбросить порядок».

Обработчики висят на `document`, а не на карточках: карточки пересоздаются при
каждой перерисовке движком панели. Атрибуты `draggable` и `data-tool` через
движок проходят нормально — проверено. Перетаскивание работает мышью; на
тач-устройствах HTML5 drag-and-drop не поддерживается.

## Как собираются адреса

Инструмент делает **два прохода** и объединяет результат: широкий поиск от центра
города (радиус до 40 км) и обход по сетке точек, в каждой точке — полная пагинация.
Дубли снимаются по координатам.

Так сделано не «на всякий случай». В `script.py` сетка появилась из-за двух
ограничений, которые оказались неверными: `page_size` можно до 50 (а не 10),
а число страниц не ограничено вовсе — выдача листается до конца, дальше приходит
404 `itemNotFound`. Казалось бы, сетку можно убрать. Но `point + radius` у 2ГИС —
не геометрический фильтр: для одних запросов `total` растёт с радиусом
(Пятёрочка/Уфа: 72 → 274), а для других скачет и падает (КанАвто/Казань: 7 при 3 км,
3 при 8 км), причём объекты из маленького радиуса в выдачу большого не попадают,
хотя лежат внутри круга.

Замер на четырёх запросах — ни одна стратегия не выигрывает:

| Запрос | Широкий поиск | Сетка 4×4 | Вместе |
|---|---|---|---|
| КанАвто / Казань | 8 | 17 | **17** |
| Пятёрочка / Уфа | 274 | 216 | **275** |
| Магнит / Казань | 315 | 259 | **326** |
| Додо Пицца / Казань | 16 | 75 | **77** |

**По умолчанию включён быстрый режим** — только широкий поиск: в большинстве
задач 100% выдачи не нужны. Сколько объектов набирать, задаётся полем «Сколько
объектов нужно» (по умолчанию 300) — поиск останавливается, как только набрал
столько, и результат подрезается ровно до лимита. Если нужна полнота, в поле
«Полнота» выбирается обход по сетке 4×4 или 6×6 — он идёт вторым проходом и
объединяется с широким. В результатах видно, сколько объектов дал каждый проход.

Проверенные пределы API: `page_size` ≤ 50, `radius` ≤ 40 000 м, страницы не
ограничены, в ответе есть `result.total`.

## Тема оформления

Переключатель светлой/тёмной темы — в шапке панели, выбор запоминается в
`localStorage`. Инструменты получают тему двумя путями: сразу через `#theme=` в
адресе iframe (чтобы не мигало) и через `postMessage` при переключении — тогда
открытый инструмент не перезагружается и не теряет результаты. Цвета вынесены в
CSS-переменные (`lib/tool-ui.css`, `lib/theme.js`).

Тему поддерживают все пять внутренних инструментов. Карта дополнительно
подбирает подложку под тему: в тёмной стартует с «Тёмной», в светлой — с
«Детальной»; дальше выбор за пользователем.

## Заметки по реализации

* **XLSX читается и пишется своим кодом**, без SheetJS — чтобы панель осталась одним
  файлом без внешних зависимостей. Распаковка — штатный `DecompressionStream('deflate-raw')`.
* **Размеры видео берутся из содержимого файла** (боксы `moov→trak→mdia→minf→stbl→stsd`),
  как в `match_creatives.py`, а не из названия. Из больших архивов читаются только
  первый и последний мегабайт каждого видео, поэтому 1,3 ГБ обрабатываются за ~10 секунд
  и память не разрастается. `ffprobe` не нужен.
* **CORS**: Яндекс.Диск отражает заголовок `Origin`, поэтому ТТ тянутся напрямую из
  браузера. 2ГИС и Nominatim идут через функции — не из-за CORS, а чтобы спрятать ключ
  и представиться Nominatim по-человечески.
* Внутри панели инструмент открывается в **blob:-документе**, а относительный `/api/…`
  от blob-адреса не разрешается. Поэтому `addresses-core.js` собирает абсолютный URL
  через `location.origin` (у blob-документа он равен origin создателя). Без этого поиск
  работал бы на отдельной странице и молча падал внутри панели.
* Движок панели (`x-dc`) **не подставляет `{{ }}` внутрь `style-hover`** —
  интерполированные свойства просто выпадают из правила. Поэтому цвета для
  `:hover` заданы CSS-переменными в `<helmet>`, а тему переключает атрибут
  `data-theme` на `<html>`.
* `User-Agent` для Nominatim только на латинице: в значение HTTP-заголовка нельзя
  положить кириллицу — `fetch` падает на преобразовании в ByteString.
* В `build.py` последовательность `</` в JSON-данных экранируется в `<` + `/` —
  иначе парсер HTML закроет `<script>` на первом же `</script>` внутри данных
  и панель не распакуется. В исходном bundle сделано так же. В `build.py` на это есть
  самопроверка, так что молча сломать сборку не получится.
